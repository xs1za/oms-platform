# Шаблон оформления задач на разработку по SMART

## 1. Шаблон задачи на разработку

```markdown
## [front/back/fullstack/report/admin/integration] Краткое название задачи

### 1. Боль

Что беспокоит бизнес или пользователей.

Указать:

- что сейчас не работает / работает неудобно / создает риск;
- кого это затрагивает;
- почему текущее поведение не устраивает.

### 2. Цель

Какого результата нужно добиться после выполнения задачи.

Цель должна быть SMART:

- конкретная (Specific): Результат описан четко и однозначно, понятен каждому исполнителю. Нет размытых формулировок;
- измеримая (Measurable): Успех поддается оценке в цифрах, процентах или конкретных метриках (KPI);
- достижимая (Achievable / Attainable): Задача реальна для выполнения с учетом имеющихся ресурсов, времени и опыта;
- релевантная (Relevant): Цель важна для компании или личного развития и не противоречит другим задачам;
- ограниченная по времени (Time bound): установлен четкий дедлайн, дата или период завершения.

### 3. Как сейчас

Описать текущее поведение.

Если есть сценарий воспроизведения:

1. Шаг 1.
2. Шаг 2.
3. Шаг 3.
4. Фактический результат.

Если раздел не нужен для маленькой задачи, указать:

_Не требуется: изменение не связано с существующим пользовательским сценарием._

### 4. Как должно быть

Описать целевое поведение после реализации.

Указать:

- кто выполняет действие;
- где выполняет действие;
- что система должна сделать;
- какие ограничения и ошибки должны быть обработаны;
- какой результат должен увидеть пользователь.

### 5. Место изменения

Указать точное место изменения.

Например:

- страница:
- раздел админки:
- модель:
- таблица:
- API-метод:
- компонент:
- отчет:
- команда / задача / интеграция:
- права доступа:

### 6. Функциональное описание

#### 6.1. Блок 1: Название блока

Описание логики.

Указать при необходимости:

- входные параметры;
- обязательные поля;
- необязательные поля;
- типы данных;
- статусы;
- проверки;
- условия отображения;
- условия доступности;
- тексты ошибок;
- события, при которых запускается логика.

#### 6.2. Блок 2: Название блока

Описание логики.

### 7. Технические требования

Заполняется, если для задачи важно явно зафиксировать технический способ реализации.

Указать:

- новые модели / поля / связи;
- изменения в существующих моделях;
- миграции;
- API-запросы и ответы;
- фоновые задачи;
- интеграции;
- настройки;
- права доступа;
- ограничения целостности;
- требования к сохранению истории;
- требования к производительности;
- требования к логированию.

Если технический способ не принципиален:

_Технический способ реализации остается на усмотрение разработки при сохранении целевого поведения._

### 8. Обязательные ограничения реализации

Указать только те требования, которые должны быть реализованы строго заданным способом.

Например:

- использовать конкретный статус:
- использовать конкретное поле:
- использовать конкретный текст:
- не менять существующий алгоритм:
- не добавлять новые настройки:
- не менять поведение в других разделах:

Если таких требований нет:

_Нет._

### 9. Макеты, схемы, иллюстрации

При необходимости приложить макеты, схемы, скриншоты.

Если макеты не нужны:

_Не требуется._

### 10. Настройки и данные для проверки

Указать:

- какие настройки должны быть включены;
- какие роли / права нужны;
- какие тестовые данные нужны;
- какие внешние сервисы / интеграции нужны;
- какие ограничения окружения есть.

Если специальных настроек нет:

_Специальные настройки не требуются._

### 11. Для QA

Указать неочевидные моменты для проверки.

Например:

- пограничные кейсы;
- негативные сценарии;
- права доступа;
- старые данные;
- миграции;
- влияние на связанные разделы;
- что точно не должно измениться.

### 12. Критерии приемки

Критерии должны быть проверяемыми.

- При условии ..., когда ..., тогда ...
- При условии ..., когда ..., тогда ...
- При условии ..., когда ..., тогда ...

### 13. Глоссарий и сокращения

Для общепринятых сокращений можно указать ссылку на внешний глоссарий в wiki.

Новые, проектные или редко используемые сокращения нужно расшифровывать в задаче.

Пример:

- ПП - платежное поручение.
- СБП - система быстрых платежей.
- QA - контроль качества / тестирование.

Если сокращений нет:

_Не требуется._

### 14. История изменений требований

Все изменения требований после первичного описания задачи фиксируются в тексте задачи.

Правила:

- неактуальный текст не удалять, а зачеркивать;
- новые требования и изменения добавлять с пометкой даты и автора / инициатора, если известно;
- рядом с изменением указывать причину или контекст, если это важно.

Пример:

~~Необходимо отображать кнопку для всех пользователей.~~

Изменено 22.05.2026: кнопку отображать только пользователям с правом `can_edit_payment`.

### 15. Вне рамок задачи

Указать явно, что не входит в задачу.

- Не меняем ...
- Не реализуем ...
- Не переносим ...
- Не дорабатываем ...

Если ограничений нет:

_Не зафиксировано._
```

## 2. Инструкция для системного аналитика

### Общие правила

1. Задача должна отвечать критериям SMART.
2. В задаче не должно быть неоднозначных формулировок: "как-нибудь", "по возможности", "и т.п.", "примерно", "желательно".
3. Аббревиатуры нужно расшифровывать при первом использовании либо указывать ссылку на глоссарий.
4. Общепринятые сокращения можно расшифровывать во внешней wiki, а в задаче указывать ссылку на соответствующий глоссарий.
5. Новые, проектные или редко используемые сокращения нужно расшифровывать в разделе `Глоссарий и сокращения` в подвале задачи.
6. Если раздел не нужен, не заполнять его случайным текстом. Лучше написать коротко: `_Не требуется._`
7. Общие продуктовые алгоритмы лучше выносить в продуктовую задачу, а в задаче на разработку оставлять только конкретные изменения для реализации.
8. Если есть строгое требование к реализации, его нужно вынести в раздел `Обязательные ограничения реализации`.
9. Если разработчик не должен сам выбирать текст, статус, название поля, условие или алгоритм, это должно быть явно указано.
10. Критерии приемки должны быть проверяемыми QA без дополнительного уточнения у аналитика.
11. Изменения требований в процессе проработки или разработки нельзя удалять бесследно.
12. Неактуальный текст нужно зачеркивать через Markdown-разметку: `~~неактуальный текст~~`.
13. Новые требования и изменения нужно добавлять с пометкой даты и автора / инициатора, если известно.

### Для больших задач

Если задача большая, рекомендуется разделять описание на блоки:

- пользовательские сценарии;
- правила отображения;
- правила валидации;
- права доступа;
- API;
- миграции;
- фоновые задачи;
- интеграции;
- критерии приемки.

### Для маленьких задач

Если задача маленькая, допускается краткое описание, но обязательными остаются:

- боль или причина изменения;
- цель;
- как должно быть;
- место изменения;
- критерии приемки;
- вне рамок задачи, если есть риски неверной трактовки.
```
